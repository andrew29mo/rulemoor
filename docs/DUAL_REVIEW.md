## Findings and changes

1. **Invalid restart process identity passed the artifact auditor.** Replacing the retained restarted service identity with PID 0/start 0 while preserving the boot still passed the complete auditor after HTML regeneration. The verifier now requires valid integer PID/start fields and the expected boot for each dual service identity; it links the stable timeout/memory sample to the same process and rejects inconsistent restarted identities.
2. **Receipts from another boot or operation could be mixed into a passing report.** Copied evidence with internally consistent failure/rollback receipts on another boot, or successful confirmations naming another operation/boot, was accepted. Every dual projection now has its boot and integer generation checked; the fixed fixture's initial, blocked, successful, partial-crash and successor operations must form their expected operation/generation sequence. Timeout and restart projections must preserve the corresponding policy and partial confirmation fields. Six additional corruption controls challenge these links and immediate stale-kernel preservation. These checks detect the tested inconsistencies; they are not cryptographic authentication of artifacts or a guarantee against all coordinated tampering.
3. **Stale-request readback was indirect.** The previous fixture checked journal state immediately after rejected requests but read kernel policy after subsequent valid confirmations. Production confirm performs readback and does not reapply policy, so a claim that ordinary confirmation would automatically hide a stale kernel mutation is not supported by the implementation. Nevertheless, the new fixture makes the evidence direct: before and after each stale confirm/cancel/apply, the host fixture reads the real journal and both kernel tables, requires unchanged successor state/policies, and exports those observations. Only afterward does it submit legitimate family confirmations.

No change to the production dual-policy compiler, confirmation state machine or TLS transport was required by the confirmed findings. ## ICMPv6 judgment

The current compiler deliberately accepts all ICMPv6 before user TCP rules, as well as established/related traffic. That matches the read-back rules and existing documentation. Preserving essential ICMPv6 is necessary for IPv6 operation, but allowing every ICMPv6 type is broader than an essential-message allowlist. Within this explicitly TCP-focused minimum slice, the permissive choice is transparent and avoids pretending to implement a complete ICMPv6 firewall. It is not suitable evidence of RA hardening, hostile-link protection, PMTU conformance or production security qualification. A restrictive profile would require its own schema/compatibility decision and packet-level validation; this review does not silently change existing policy meaning.

[RFC 4890](https://www.rfc-editor.org/rfc/rfc4890.html) distinguishes essential and deployment-dependent ICMPv6 traffic. [RFC 4861](https://www.rfc-editor.org/rfc/rfc4861.html) specifies neighbour/router discovery validation; the permissive firewall rule does not authenticate a neighbour or router. Local OS checks and other firewall managers remain relevant, and Rulemoor does not modify their rules.
